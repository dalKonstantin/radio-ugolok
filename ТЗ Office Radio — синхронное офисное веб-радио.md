# ТЗ: Radio Ugolok — синхронное офисное веб-радио

Nov 2, 2026 · @Konstantin

## Цель и сценарий

Radio Ugolok — внутреннее веб-радио для офиса: один общий эфир, который все слушают в наушниках синхронно, с расхождением между клиентами менее 150 мс.

Основной сценарий: сотрудник открывает страницу во внутренней сети, жмёт «Подключиться к эфиру» и сразу попадает в середину играющего трека. Загружает свой mp3 перетаскиванием, ставит его в очередь — трек играет у всех одновременно.

Контекст, определяющий требования:

- Слушают в наушниках, общих колонок нет. Sample-accurate синхронизация не нужна, но ощущение «играет одно и то же» должно быть устойчивым.
- Эфир играет только то, что поставили в очередь. Пустая очередь — тишина и заглушка на экране; радио ничего не подбирает само.
- Доверенная среда, внутренняя сеть. Авторизации нет; пользователь задаёт ник, он хранится в `localStorage` и уходит на сервер при подключении.
- Нагрузка: 10–30 одновременных слушателей, библиотека до нескольких тысяч треков, исходные файлы до 150 МБ.
- Принимаем любой распространённый аудиоформат — mp3, flac, wav, ogg, opus, m4a. В эфир всё идёт одним форматом после перекодирования на загрузке.

## Стек и ограничения

Всё собирается в один бинарник: фронтенд вшит через `embed.FS`, внешних сервисов нет, кроме `ffmpeg`/`ffprobe` в PATH.

| Слой | Решение | Почему |
| --- | --- | --- |
| Бэкенд | Go 1.23+ | Стандартная библиотека покрывает HTTP, Range, multipart |
| WebSocket | `github.com/coder/websocket` | Актуальная, контекстная, без лишних абстракций |
| Хранилище метаданных | SQLite через `modernc.org/sqlite` | Чистый Go, без cgo — кросс-компиляция остаётся простой |
| Эфирные файлы | mp3 на диске в `data/tracks/` | Раздаются через `http.ServeContent` |
| Теги и обложки | `github.com/dhowden/tag` | Читает ID3, MP4-атомы и Vorbis comments — все нужные контейнеры |
| Перекодирование, длительность, пики | `ffmpeg` и `ffprobe` в PATH | Жёсткая зависимость: без них загрузка не работает |
| Фронтенд | Vanilla JS (ES2022 modules) + CSS, без сборки | Нет npm-шага, файлы отдаются как есть |

Запрещено без отдельного согласования: фронтенд-фреймворки и бандлеры, ORM, брокеры сообщений, Redis, транскодирование при раздаче — перекодирование делается один раз, на загрузке. Состояние эфира живёт в памяти процесса; в SQLite лежат только библиотека и загруженные пики.

Поддерживаемые браузеры: актуальные Chrome, Firefox, Safari на десктопе. Вёрстка адаптивная до 768 px, но мобильный Safari не является целевой платформой.

## Архитектура

Сервер — единственный источник правды о том, что играет. Клиент не хранит состояние эфира: он получает его рассылкой и сам подгоняет себя под него.

&#91;embedded content: архитектура · 8 компонентов, два канала между браузером и сервером\]

Два канала работают независимо. По WebSocket идёт только состояние и команды — несколько килобайт в минуту. Аудио едет обычным HTTP-запросом с заголовком `Range`, минуя WebSocket целиком, и кешируется браузером навсегда.

`station` — единственный владелец состояния эфира, живёт в своей горутине. `hub` не трогает его поля напрямую: команды идут в канал автомата, обратно приходят готовые сообщения для рассылки. Блокировок в проекте быть не должно.

Модель данных в SQLite — одна таблица:

```sql
CREATE TABLE tracks (
  id          TEXT PRIMARY KEY,  -- sha256 содержимого файла
  title       TEXT NOT NULL,
  artist      TEXT NOT NULL,
  album       TEXT,
  duration_ms INTEGER NOT NULL,  -- из ffprobe, не из тегов
  size_bytes  INTEGER NOT NULL,
  has_cover   INTEGER NOT NULL DEFAULT 0,
  peaks       BLOB,              -- 1000 байт, 0-255
  uploaded_by TEXT,
  uploaded_at INTEGER NOT NULL,  -- Unix ms
  played_at   INTEGER            -- Unix ms, NULL пока трек не звучал
);

CREATE INDEX idx_tracks_title  ON tracks(title);
CREATE INDEX idx_tracks_artist ON tracks(artist);
```

Очередь, слушатели и голоса в базу не пишутся — они живут только в памяти и умирают вместе с процессом.

## Протокол WebSocket

Один эндпоинт `GET /ws`. Все сообщения — JSON в конверте `{"type": "...", "data": {...}}`. Все отметки времени — `int64`, Unix-миллисекунды.

Сообщения сервер → клиент:

| type | data | Когда |
| --- | --- | --- |
| `hello` | `clientId`, `serverTime` | Сразу после апгрейда |
| `pong` | `t0` (эхо клиента), `tServer` | На каждый `ping`, отправляется без очереди |
| `state` | `nowPlaying`, `queue[]`, `listeners`, `skip`, `chat[]` | После `join` и по запросу `resync` |
| `nowPlaying` | `track`, `startedAt`, `duration`, `source` | При смене трека |
| `queue` | `items[]` | Любое изменение очереди |
| `listeners` | `count`, `nicks[]` | Вход и выход слушателя |
| `skip` | `votes`, `required` | Изменение голосов за скип |
| `chat` | `id`, `nick`, `text`, `at`, `kind` | Новое сообщение или системное событие |
| `trackRemoved` | `trackId` | Трек удалён из библиотеки |
| `trackAdded` | `track` | Загружен новый трек |
| `error` | `code`, `message` | Отказ на команду клиента |

Сообщения клиент → сервер:

| type | data | Эффект |
| --- | --- | --- |
| `join` | `nick` | Регистрирует слушателя, в ответ `state` |
| `ping` | `t0` | Запрос такта для оценки сдвига часов |
| `enqueue` | `trackId` | Добавляет трек в конец очереди |
| `dequeue` | `itemId` | Убирает позицию из очереди |
| `voteSkip` | — | Голос за пропуск текущего трека, повторный снимает голос |
| `chat` | `text` | Отправляет сообщение в общую комнату |
| `deleteTrack` | `trackId` | Удаляет отыгравший трек из библиотеки |
| `resync` | — | Запрос свежего `state` |

Форма `nowPlaying`:

```json
{
  "track": {
    "id": "9f2c...",
    "title": "Midnight City",
    "artist": "M83",
    "durationMs": 243000,
    "hasCover": true
  },
  "startedAt": 1762085412345,
  "addedBy": "kostya"
}
```

Когда очередь пуста, `nowPlaying` приходит с `track: null` и без `startedAt`. Это нормальное состояние, а не ошибка: радио молчит, пока кто-нибудь не поставит трек.

Живучесть соединения: клиент шлёт WebSocket-ping каждые 20 с, сервер закрывает соединение без ответа через 60 с. Клиент переподключается с экспоненциальной задержкой от 1 до 15 с и после каждого переподключения заново оценивает сдвиг часов.

## Алгоритм синхронизации

Это ядро проекта. Сервер не стримит аудио — он сообщает, какой трек и с какой отметки времени играет, а клиент сам ставит себя в нужную точку файла и удерживается в ней.

### Шаг 1. Оценка сдвига часов

При подключении и далее раз в 60 с клиент делает 10 обменов `ping`/`pong` с интервалом 200 мс:

1. Клиент запоминает `t0 = Date.now()` и шлёт `ping`.
2. Сервер немедленно отвечает `pong` с эхом `t0` и своим `tServer`. Ответ формируется вне общей очереди рассылки, чтобы не ловить её задержку.
3. Клиент фиксирует `t1 = Date.now()` и считает `offset = tServer - (t0 + t1) / 2`, `rtt = t1 - t0`.

Из 10 образцов берутся 3 с наименьшим `rtt`, итоговый `offset` — медиана их значений. Это отсекает выбросы на загруженной сети. Серверное время считается от монотонных часов, привязанных к одной точке старта процесса, чтобы перевод системного времени не ломал эфир.

### Шаг 2. Выход в позицию

```js
const LOOKAHEAD = 0.3; // с, запас на буферизацию и декод
const targetPos = (Date.now() + offset - startedAt) / 1000;

audio.src = `/api/tracks/${track.id}/audio`;
audio.preservesPitch = true;          // + webkitPreservesPitch для Safari
audio.currentTime = targetPos + LOOKAHEAD;
await once(audio, 'canplay');
await audio.play();
```

Если `targetPos` больше длительности трека, значит состояние устарело — клиент шлёт `resync` и ничего не играет до ответа.

### Шаг 3. Удержание

Проверка дрейфа вешается на событие `timeupdate` (срабатывает около 4 раз в секунду) с подстраховкой `setInterval` на 2 с: таймеры в фоновых вкладках душатся браузером, а воспроизведение — нет.

На каждой проверке `drift = targetPos - audio.currentTime` в секундах, положительный означает, что клиент отстаёт:

| Дрейф | Действие |
| --- | --- |
| менее 0,05 с | `playbackRate = 1`, ничего не делаем |
| от 0,05 до 1 с | `playbackRate = 1 + clamp(drift * 0.1, -0.02, 0.02)` |
| более 1 с | жёсткий `currentTime = targetPos + 0.1`, затем `playbackRate = 1` |

Отклонение темпа в 2 % на слух незаметно и выбирает 0,2 с расхождения примерно за 10 секунд. После жёсткой перемотки проверки приостанавливаются до события `seeked`, иначе алгоритм начнёт гоняться за собственным отставанием.

### Шаг 4. Диагностика

В углу интерфейса — мелкий технический индикатор: текущий `offset`, медианный `rtt`, мгновенный дрейф в миллисекундах и текущий `playbackRate`. Он нужен и при разработке, и чтобы в офисе можно было быстро сказать, у кого именно расходится.

## Логика эфира

Эфир — одна горутина-конечный автомат, владеющая всем состоянием. Соединения не трогают состояние напрямую: команды приходят в её канал, наружу уходят готовые широковещательные сообщения. Это снимает вопрос блокировок целиком.

Состояние в памяти: текущий трек, `startedAt`, очередь, множество слушателей, множество голосов за скип. Переживать перезапуск оно не обязано — после рестарта эфир просто начинается заново со случайного трека.

### Переключение треков

После старта трека автомат ставит `time.Timer` на `duration - elapsed + 500 мс`. Запас в полсекунды гарантирует, что клиенты успеют доиграть хвост, а не оборвутся за миг до конца. По срабатыванию:

1. Если очередь непуста — берётся первая позиция, `startedAt` ставится в момент срабатывания таймера, всем уходит `nowPlaying`.
2. Если пуста — эфир переходит в состояние `idle` и рассылает `nowPlaying` с `track: null`. Клиенты останавливают звук и показывают заглушку «Эфир пуст — поставьте трек в очередь».
3. Из `idle` эфир выходит сразу, как только в очередь попадает первый трек: `startedAt` ставится в момент постановки, таймер заводится заново.

Радио не подбирает треки само: шафла по библиотеке нет. Если никто ничего не поставил, в офисе тихо — это задуманное поведение, а не дыра в логике.

### Очередь

Очередь — список позиций, у каждой свой `itemId`, `trackId` и ник добавившего. Один и тот же трек может стоять в очереди несколько раз. Убрать позицию может любой — это офисное радио, а не система прав.

Ограничение против захвата эфира: от одного ника в очереди не более 3 позиций одновременно. Попытка добавить четвёртую получает `error` с кодом `queue_limit`.

### Голосование за скип

Скип требует голосов более чем от половины подключённых слушателей, минимум два голоса. При одном слушателе он скипает сразу — спорить не с кем.

Голоса привязаны к `clientId` и сбрасываются при каждой смене трека. Повторный `voteSkip` от того же клиента снимает голос. Когда порог взят, автомат переключает трек немедленно, как по таймеру.

### Удаление отыгравших треков

Отыгравший трек можно удалить — библиотека наполняется разовыми загрузками и без чистки зарастает.

Удаление ручное. У трека, который уже звучал хотя бы раз, в библиотеке появляется крестик. Команда `deleteTrack` убирает запись из SQLite, mp3, обложку и все позиции этого трека из очереди, затем рассылается `trackRemoved`.

Играющий сейчас трек удалить нельзя: `error` с кодом `track_playing`, крестик на нём неактивен. Флаг `played_at` в таблице `tracks` отмечает, что трек уже звучал.

Автоудаление сразу после проигрывания тоже есть, но выключено по умолчанию — флаг `-ephemeral`. При нём трек стирается через 5 секунд после смены, и библиотека живёт только тем, что принесли сегодня.

## Чат

Рядом с эфиром живой чат: одна общая комната, без тредов, личных сообщений и редактирования.

Сообщения живут в кольцевом буфере на 200 последних внутри автомата эфира. В SQLite они не пишутся и перезапуск не переживают — это осознанный выбор, а не упрощение.

Форма сообщения:

```json
{ "id": "m-8421", "nick": "kostya", "text": "ставьте что-нибудь бодрое", "at": 1762085412345, "kind": "user" }
```

`kind` принимает значения `user` и `system`. Системные события идут в той же ленте серым курсивом: кто подключился и ушёл, кто добавил трек, чей скип прошёл.

### Ограничения

- Длина до 500 символов: обрезка на клиенте, проверка на сервере, при превышении — `chat_too_long`.
- Не более 5 сообщений за 10 секунд от одного `clientId`, дальше — `chat_flood`.
- Текст вставляется только через `textContent`. `innerHTML` запрещён даже во внутренней сети.
- Ссылки не разбираются и не делаются кликабельными. Картинок и файлов в чате нет.

### Интерфейс

На ширине от 1280 px чат — третья колонка справа на всю высоту под проигрывателем, уже — сворачиваемая панель снизу.

Строка: ник оранжевым 12 px полужирным, текст 13 px, время 11 px серым справа. Подряд идущие сообщения одного человека группируются — ник показывается один раз.

Автопрокрутка вниз работает, пока пользователь не отлистал вверх; тогда внизу появляется оранжевая плашка «Новые сообщения». При свёрнутой панели непрочитанные показываются оранжевым бейджем со счётчиком.

Поле ввода внизу, Enter отправляет, Shift+Enter не переносит строку — сообщения однострочные.

## Загрузка треков

`POST /api/upload`, `multipart/form-data`, поле `file`, лимит 150 МБ через `http.MaxBytesReader`. Обработка синхронная: ответ приходит, когда файл перекодирован и готов к постановке в очередь. Пятиминутный flac перекодируется за несколько секунд, wav дольше, поэтому одновременных задач не больше двух — семафор на входе.

Последовательность:

1. **Формат определяется содержимым, а не расширением.** `ffprobe -show_streams` должен найти ровно один аудиопоток в одном из принимаемых контейнеров: mp3, flac, wav, aiff, ogg с Vorbis, opus, m4a с AAC или ALAC, wma. Всё остальное — `415` с кодом `unsupported_format`. Расширение не проверяется вообще.
2. **Дедупликация по SHA-256 исходного файла.** Хеш становится `trackId`. Тот же файл, загруженный второй раз, возвращает `200` с существующей записью, а не создаёт дубль.
3. **Перекодирование в эфирный формат** (ниже). Результат ложится в `data/tracks/<hash>.mp3`; исходник не сохраняется.
4. **Длительность через `ffprobe` по готовому mp3**, а не по оригиналу: играет именно он, и на его длительности держится вся синхронизация.
5. **Метаданные через `dhowden/tag`** читаются из оригинала до перекодирования: title, artist, album, встроенная обложка. Тегов нет — title берётся из имени файла без расширения, artist становится `Unknown`.
6. **Обложка** сохраняется в `data/covers/<hash>.jpg`, уменьшенная до 500×500.
7. **Пики waveform** считаются один раз и кладутся в SQLite.

### Эфирный формат

Что бы ни загрузили, в эфир идёт MP3 192 kbps CBR, 44,1 кГц, стерео:

```
ffmpeg -i <input> -vn -ac 2 -ar 44100 -codec:a libmp3lame \
       -b:a 192k -write_xing 1 -f mp3 data/tracks/<hash>.mp3
```

Единый формат вместо раздачи оригиналов — по трём причинам:

- **Браузеры расходятся по кодекам.** Safari не играет Ogg Vorbis, поддержка Opus и FLAC неровная, ALAC в m4a мимо почти везде. Один mp3 играет у всех без исключений.
- **CBR перематывается точно.** Это главное. Клиент ставит `currentTime` в вычисленную точку, а у VBR-файла без корректного заголовка Xing он промахивается на секунды — и синхронизация, ради которой всё затевалось, разъезжается.
- **Размер.** Пять минут wav весят около 50 МБ, те же пять минут в 192 kbps — около 7 МБ. Этот файл едет по сети каждому слушателю.

В наушниках 192 kbps от исходника на слух не отличается. Если захочется выше, битрейт выносится во флаг `-bitrate`, но формат остаётся один.

### Расчёт пиков

Пики считаются по готовому эфирному mp3, а не по оригиналу — рисовать надо ровно то, что слышно. `ffmpeg -i <hash>.mp3 -ac 1 -ar 8000 -f s16le -` даёт моно-PCM, он делится на 1000 равных корзин, в каждой берётся максимум модуля и нормируется в 0–255. Получается 1000 байт — они уходят клиенту и рисуют полосу.

`ffmpeg` и `ffprobe` проверяются при старте сервера. Если их нет в PATH, процесс не поднимается и пишет в лог, чего не хватает. Запасного пути без них нет: без перекодирования половина форматов просто не заиграет в браузере.

## HTTP API

| Метод и путь | Назначение | Ответ |
| --- | --- | --- |
| `GET /` | SPA из `embed.FS` | `text/html` |
| `GET /ws` | Апгрейд в WebSocket | `101` |
| `GET /api/state` | Снимок эфира для диагностики и курла | JSON |
| `GET /api/library?q=&limit=&offset=` | Библиотека с поиском по title и artist | JSON |
| `POST /api/upload` | Загрузка аудиофайла | JSON с треком |
| `GET /api/tracks/{id}/audio` | Сам аудиофайл | `audio/mpeg` |
| `GET /api/tracks/{id}/cover` | Обложка, `404` если нет | `image/jpeg` |
| `GET /api/tracks/{id}/peaks` | 1000 байт пиков | `application/octet-stream` |

Постановка в очередь, удаление и голосование идут только через WebSocket — так клиенты получают обновление сразу, без отдельного round-trip.

### Раздача аудио

Только `http.ServeContent` с открытым `*os.File`. Он сам отдаёт `Accept-Ranges`, обрабатывает `Range` и `If-Range`, выставляет `Last-Modified` — без этого клиент не сможет перемотаться в середину трека, и вся схема рассыплется.

Имя файла — хеш содержимого, значит содержимое по URL неизменно: `Cache-Control: public, max-age=31536000, immutable` и `ETag` по хешу. Второй раз трек по сети не поедет.

То же для обложек и пиков.

### Ошибки

Единый вид тела ошибки для всех эндпоинтов:

```json
{ "error": { "code": "not_mp3", "message": "Файл не похож на mp3" } }
```

Коды: `unsupported_format`, `too_large`, `probe_failed`, `transcode_failed`, `not_found`, `queue_limit`, `unknown_track`, `track_playing`, `chat_flood`, `chat_too_long`. Сообщения на русском — они показываются пользователю как есть.

## Фронтенд

Визуальный ориентир — SoundCloud: светлый серый фон, белые карточки, тонкие границы, оранжевый как единственный акцентный цвет и оранжево-тёмный градиент в шапке проигрывателя. Интерфейс плоский, скругления минимальные, теней почти нет.

### Палитра и типографика

```css
:root {
  --orange:        #FF5500;  /* акцент, фирменный оранжевый */
  --orange-hover:  #FF7700;
  --orange-dark:   #CC3300;  /* нижняя точка градиента шапки */
  --bg:            #F2F2F2;  /* фон страницы */
  --surface:       #FFFFFF;  /* карточки, строки списков */
  --border:        #E5E5E5;
  --row-hover:     #F2F2F2;
  --text:          #333333;
  --text-muted:    #999999;
  --wave-played:   #FF5500;
  --wave-pending:  #CCCCCC;
  --radius:        3px;
  --font: 'Inter', -apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, Helvetica, Arial, sans-serif;
}
```

Базовый кегль 14 px, вторичный текст 12 px, микроподписи 11 px, название играющего трека 24 px. SoundCloud использует шрифт Interstate — он проприетарный, берём Inter как ближайший практичный аналог, подключённый локально, без обращения к CDN.

### Экран

1. **Шапка**, высота 46 px, фон `--surface`, снизу граница `--border`. Слева логотип «Radio Ugolok» — слово «Ugolok» оранжевое. По центру индикатор эфира: пульсирующая оранжевая точка 8 px и «12 слушателей». Справа оранжевая кнопка «Загрузить трек».
2. **Проигрыватель**, на всю ширину, фон `linear-gradient(135deg, var(--orange), var(--orange-dark))`, высота около 280 px. Слева обложка 220×220 без скругления, с лёгкой тенью; при отсутствии обложки — оранжево-серая заглушка с нотой. Справа: исполнитель 12 px полупрозрачным белым, название 24 px белым, ниже waveform, под ним прошедшее и общее время и ник добавившего.
3. **Колонки** на ширине от 1000 px: слева «Очередь», справа «Библиотека»; от 1280 px справа добавляется чат. Уже — складываются в одну, чат уходит в сворачиваемую панель.
4. **Тосты** в левом нижнем углу, фон `#333`, белый текст, живут 4 секунды.

### Waveform

Центральная деталь стиля. Рисуется на `<canvas>` по 1000 байт пиков: столбики шириной 3 px с зазором 1 px, высота от значения пика.

Верхняя часть — полная высота, нижняя — зеркальная копия в 35 % высоты и с прозрачностью 0,4, как на SoundCloud. Проигранная часть белая, непроигранная — белая с прозрачностью 0,35; граница между ними двигается по тому же `targetPos`, что считает синхронизация, а не по `audio.currentTime`, чтобы картинка не дёргалась при коррекции темпа.

Waveform **не кликабельна**: эфир общий, перемотка невозможна. Курсор остаётся обычным, при наведении — подсказка «Эфир общий, перемотка недоступна». Это надо заложить сразу, иначе пользователи будут по ней щёлкать.

### Управление

Кнопки play/pause в привычном смысле нет. Есть переключатель «Подключиться / Отключиться»: отключение останавливает звук локально, подключение всегда возвращает в текущую точку эфира, а не туда, где человек ушёл. Рядом ползунок громкости с оранжевой заполненной частью.

**Гейт автозапуска.** При первом открытии — оверлей на весь экран с тёмно-оранжевым градиентом и круглой оранжевой кнопкой 80 px. Без клика браузер звук не даст, поэтому оверлей обязателен; заодно это момент, когда делается первый выход в позицию.

### Списки

Строка очереди, 48 px: номер позиции серым, название и исполнитель, ник добавившего справа, крестик удаления появляется при наведении. Фон строки белый, при наведении `--row-hover`.

Библиотека: поле поиска сверху, под ним строки с обложкой 40×40, названием и исполнителем, длительностью и кнопкой «+» при наведении. Поиск фильтрует с задержкой 200 мс и уходит на сервер.

Загрузка: кнопка в шапке плюс приём файлов перетаскиванием на всю страницу. При перетаскивании — оранжевая рамка по периметру окна и подпись «Отпустите, чтобы загрузить». Прогресс — тонкая оранжевая полоса под шапкой.

### Диагностика

В правом нижнем углу мелкий моноширинный блок 11 px цветом `--text-muted`, сворачиваемый: `offset`, `rtt`, дрейф в миллисекундах, `playbackRate`. По умолчанию свёрнут.

JS разбить по модулям: `sync.js` (часы и удержание позиции), `player.js` (audio-элемент), `waveform.js` (canvas), `ws.js` (соединение и переподключение), `ui.js` (рендер), `upload.js`.

Конфигурация — флаги с переменными окружения как запасным источником:

| Флаг | По умолчанию | Смысл |
| --- | --- | --- |
| `-addr` | `:8080` | Адрес прослушивания |
| `-data` | `./data` | Корень хранилища |
| `-max-upload` | `150` | Лимит загрузки, МБ |
| `-bitrate` | `192` | Битрейт эфирного mp3, kbps |
| `-queue-limit` | `3` | Позиций в очереди на одного человека |
| `-ephemeral` | выключен | Удалять трек через 5 секунд после проигрывания |

Запуск: `make run` поднимает сервер на `localhost:8080`. `make build` собирает один бинарник. Dockerfile многостадийный, финальный образ на `alpine` с установленным `ffmpeg`, `data` вынесена в volume.

README содержит: что это, как запустить за две команды, как работает синхронизация в пяти предложениях, как проверить сборку. Схема SQLite создаётся миграцией при старте, отдельного шага нет.

Тесты: юнит-тест на выбор следующего трека и исключение истории, юнит-тест на подсчёт голосов за скип, тест на медианную оценку `offset` по набору образцов с выбросами. Полного покрытия не требуется.

## Этапы

Четыре этапа, каждый заканчивается чем-то работающим. Не переходить к следующему, пока предыдущий не проверен вживую в двух браузерах.

1. **M1 — синхронизация на одном треке.** Go-сервер, WebSocket, оценка сдвига часов, выход в позицию, коррекция дрейфа. Трек захардкожен, интерфейса почти нет — голая страница, кнопка «Подключиться» и блок диагностики. Это самый рискованный кусок, поэтому он первый. Проверка: две вкладки в разных браузерах играют в унисон, дрейф на индикаторе держится в пределах 50 мс.
2. **M2 — библиотека и загрузка.** SQLite, `POST /api/upload`, дедупликация, `ffprobe`, теги, обложки, пики. Раздача через `ServeContent` с Range. Список треков без оформления. Проверка: flac и wav загружаются, превращаются в эфирный mp3 и играют в браузере; повторная загрузка того же файла не создаёт дубль.
3. **M3 — эфир.** Автомат с очередью, авто-переключение по таймеру, молчание при пустой очереди, голосование за скип, счётчик слушателей, чат. Проверка: трек доигрывает до конца и сам сменяется следующим из очереди, опоздавший попадает в середину.
4. **M4 — интерфейс.** Полная вёрстка в стиле SoundCloud, градиентный проигрыватель, waveform на canvas, гейт автозапуска, перетаскивание файлов, тосты, адаптив. Проверка: критерии приёмки ниже выполняются целиком.

Если время кончается, M4 можно урезать до простой вёрстки — радио останется рабочим. Урезать M1 нельзя: без точной синхронизации проект теряет смысл.

## Критерии приёмки

Проект считается готовым, когда выполняются все пункты. Проверять на двух физических машинах в одной сети, а не на двух вкладках одного браузера — вкладки делят часы и скрывают половину проблем.

- [ ] Два клиента на разных машинах играют один трек; измеренное расхождение не превышает 150 мс, на слух в наушниках не ловится.
- [ ] Клиент, подключившийся на середине трека, попадает в ту же точку, что остальные, и не перематывается в начало.
- [ ] Перезагрузка страницы возвращает в текущую точку эфира за время не более 2 секунд.
- [ ] Искусственный дрейф (перемотка через консоль на 3 секунды) выправляется автоматически менее чем за 15 секунд.
- [ ] Разрыв сети на 30 секунд: клиент переподключается сам и возвращается в эфир без действий пользователя.
- [ ] В интерфейсе нет ни одного способа перемотать или поставить эфир на паузу: клик по waveform ничего не делает.
- [ ] Загружаются и играют mp3, flac, wav, ogg, opus и m4a; в Chrome, Firefox и Safari все они звучат одинаково и перематываются точно.
- [ ] Файл без аудиопотока — например, текст, переименованный в `.mp3` — отклоняется с понятным сообщением.
- [ ] Повторная загрузка того же файла не создаёт второй записи.
- [ ] Трек доигрывает до конца и сам сменяется следующим из очереди без действий пользователя.
- [ ] При пустой очереди эфир замолкает и показывает заглушку; с появлением первого трека снова стартует у всех одновременно.
- [ ] Голосование за скип переключает трек при превышении половины голосов.
- [ ] Отыгравший трек удаляется из библиотеки вместе с файлом и обложкой; играющий удалить нельзя.
- [ ] Сообщение в чате появляется у всех подключённых менее чем за секунду.
- [ ] Новый клиент после `join` видит последние сообщения, а не пустой чат.
- [ ] Сообщение с HTML-тегами отображается как текст и ничего не исполняет.
- [ ] Перезапуск сервера не ломает библиотеку; эфир поднимается в `idle` с пустой очередью.
- [ ] Интерфейс не разваливается на ширине 1280 px и складывается в одну колонку на 768 px.

## Вне объёма

Сознательно не делаем в первой версии, чтобы не растить проект:

- Авторизацию, роли и права. Ник без пароля, доверенная сеть.
- Личные плейлисты, лайки, историю прослушиваний по пользователям.
- Перемотку и паузу внутри общего эфира — это противоречит самой идее.
- Несколько параллельных каналов или комнат. Эфир ровно один.
- Загрузку по ссылке, импорт из стриминговых сервисов, поиск по внешним каталогам.
- Мобильное приложение и оптимизацию под мобильный Safari.
- Треды, личные сообщения, реакции и редактирование в чате. История чата не хранится на диске.
- HTTPS и проксирование — это забота внешнего nginx, не приложения.
- Хранение оригиналов загруженных файлов и скачивание треков из библиотеки. После перекодирования исходник стирается.

Отдельно про правовую сторону: сервис рассчитан на треки, которые сотрудники загружают сами, и работает только внутри сети. Делать его доступным снаружи не нужно.
